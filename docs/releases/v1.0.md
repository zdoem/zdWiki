## 1. Architecture Overview

zdWiki is built on a local-first, decoupled architecture comprising a high-performance Python/FastAPI backend, a typed Next.js 14 web client, and an extensible CLI:

```text
               +-------------------------------------------------+
               |              zdWiki Next.js 14 UI               |
               |  (Search, Knowledge Catalog, Graph, Ask, Loops) |
               +-----------------------+-------------------------+
                                       | HTTP / JSON REST
                                       v
               +-------------------------------------------------+
               |             FastAPI Backend & Typer CLI         |
               +-----------+-------------------------+-----------+
                           |                         |
               +-----------v-----------+ +-----------v-----------+
               |  Markdown Repository  | |  SQLite FTS5 Engine   |
               |  (Sole Canonical SoT) | |  (Derived Index)      |
               +-----------+-----------+ +-----------+-----------+
                           |                         |
                           +------------+------------+
                                        |
               +------------------------v------------------------+
               |              Bounded Context Retrieval          |
               |              & LLM Provider Abstraction         |
               +-------------------------------------------------+
```

## 2. Non-Negotiable Architectural Invariants

1. **Markdown is Canonical**:
   All knowledge objects are stored on the filesystem as UTF-8 Markdown documents with strict YAML frontmatter (`knowledge/wiki/` and `knowledge/sources/`).
2. **SQLite is Disposable**:
   The SQLite database with FTS5 (`var/zdwiki.db`) is purely a derived search index and graph cache. Deleting it incurs zero loss of canonical knowledge; it can be reconstructed from scratch in milliseconds via `zdwiki index` or `rebuild_index()`.
3. **Raw Sources are Immutable**:
   All ingested artifacts are archived immutably in `knowledge/raw/{category}/{sha256_prefix}_{filename}` and verified with SHA-256 digests. Raw content is never modified or overwritten.
4. **Safe LLM Prompt Boundaries**:
   Raw source text and user knowledge objects are passed to LLMs strictly as DATA inside structured context blocks. Hostile prompt injections within sources cannot override system guidelines or execute administrative functions.
5. **Bounded Context Retrieval**:
   zdWiki rejects unconstrained token dumping. Contexts are selected deterministically via BM25 full-text search, scored, and constrained to explicit token limits (default 6,000 tokens) before calling LLM providers.
6. **Provider Independence**:
   Core system layers (`KnowledgeRepository`, `SearchEngine`, `IngestionPipeline`, `KnowledgeLinter`) contain zero vendor-specific LLM imports. Providers implement the `BaseLLMProvider` interface (`GeminiProvider`, `MockLLMProvider`).

Canonical knowledge objects conform to 11 standardized types:

| Type | Kebab Prefix | Directory Location | Primary Purpose |
| :--- | :--- | :--- | :--- |
| `concept` | `concept-` | `knowledge/wiki/concepts/` | Fundamental engineering models and domain definitions |

## 4. The Engineering Loop & Learn Mechanism

zdWiki enforces the disciplined cycle:

$$\text{Goal} \rightarrow \text{Context} \rightarrow \text{Plan} \rightarrow \text{Implement} \rightarrow \text{Test} \rightarrow \text{Diagnose} \rightarrow \text{Fix} \rightarrow \text{Re-test} \rightarrow \text{Verify} \rightarrow \text{Learn} \rightarrow \text{Persist}$$

### Verified Evidence Gate
No engineering loop may transition to `verified` without reproducible evidence (e.g. passing test suite output or trace metrics).

### Learn Stage Compilation
Upon verification, the loop compiles lessons directly into canonical knowledge objects (`bug`, `test`, `debug_playbook`). The derived index is immediately updated, making the newly captured lessons instantly retrievable by subsequent search queries and Ask sessions.

## 5. Security & Isolation Controls

* **Filename Sanitization**: Raw files are ingested with `Path(filename).name` sanitization, preventing directory traversal attacks.
* **ID Regex Enforcement**: All knowledge identifiers must strictly match `^[a-z0-9-]+$`.
* **Zero Secret Commitment**: `.env.example` provides blank configuration templates; no API tokens or passwords reside in git.
* **Data-First LLM Isolation**: Prompts enclose context within explicit data markers:
  ```text
  VERIFIED KNOWLEDGE BASE CONTEXT:
  --- KNOWLEDGE OBJECT ---
  ID: concept-jwt-auth
  ...
  ```

## 6. Backup & Disaster Recovery Standard

### Durable Assets
* `knowledge/` (Markdown canonical catalog)
* `knowledge/raw/` (Immutable source archives)
* `config/` and application source code

### Disposable Assets
* `var/zdwiki.db` (SQLite search and graph index)
* `.next/`, `__pycache__/`, `.pytest_cache/`

### Recovery Procedure
```bash
# In a new or wiped environment with canonical knowledge restored:
python zdwiki.py init
python zdwiki.py index
python zdwiki.py lint
```
*Disaster recovery verified: 100% data, graph, and searchability restored with 0 database dependencies.*
